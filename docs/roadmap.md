# Дорожная карта RF Online

Обновлено 2026-11-04. Цель: собираемая реализация с проверенной совместимостью
с одним закреплённым клиентом 455. Идентичные оригинальные исходники не обещаются.
Клиент, исходный CCR-сервер и GoMMO рассматриваются как разные системы.

## Этапы и критерии перехода

| Этап | Результат | Критерий готовности | Зависимость / модель |
|---|---|---|---|
| M0. Подготовка и статический аудит | Git, IDA MCP, 14 проектов/41 CFG, блокеры | Выполнено; исходные 962 файла неизменны | Sol medium |
| M1. Старая сборка | LoginServer Win32 Debug, описание среды | Две чистые сборки PE x86, успешная линковка, закреплённые версии/входы | B01; Sol medium, high при ABI-проблемах |
| M2. Эталоны анализа | Копии текущего клиента и backup, IDB, карта различий | SHA-256/base/архитектура установлены, изменения локализованы | Можно до M1; Sol high |
| M3. Один формат 455 | Спецификация, парсер, тестовый набор | Реальные образцы, границы, повреждённые входы; round trip при наличии writer | M2 + старый загрузчик; Sol high |
| M4. Старый клиент | SDK/Character/JPEG/zip, include/link, собираемый клиент | B02–B08 закрыты либо замены проверены по контрактам; сборка проходит | M1; Sol high, Astra точечно |
| M5. Первая функция 455 | Загрузка выбранного ресурса и его наблюдаемое использование | Контракты старой/новой версии описаны, результат сверен с эталоном | M3 + M4; Sol high |
| M6. Локальная сеть | Login/account и минимальный сценарий входа | Пакеты/состояния/ошибки и серверная роль подтверждены проверками | M5 + решение по серверу/БД; Sol high |
| M7. Расширение | Персонаж, мир, инвентарь, бой, навыки, квесты/UI по одному | Для подсистемы: контракт, реализация, эталонные примеры, регрессии | После первого полного сценария; Sol high |
| M8. Компилятор | Современная сборка без изменения поведения | Те же тесты/форматы/сценарии; отдельная ветка | Стабильный базис M5–M7; Sol high |
| M9. Графика | Новый графический путь по отдельной спецификации | Визуальные эталоны, производительность, корректность ресурсов | После базовой совместимости, отдельный проект |

M4/M6 — точки пересмотра объёма: утраченные Character SDK и сервер мира могут
потребовать самостоятельной реализации. Заглушка не считается восстановленным
контрактом. Срок полного проекта неизвестен. После M3 оценить реальные затраты на
один формат и уточнить оценки подсистем; количество декомпилированных функций не
является мерой готовности.

## Ближайшая очередь

1. Найти установочные материалы VC6/SP6 и Win32 SDK, подтвердить доступную VM.
   Закрепить версии/хеши и снимок среды.
2. Подготовить копию LoginServer с общими каталогами под work/legacy-build.
   Сначала исходные Debug-флаги; исправления — отдельными небольшими патчами.
3. Получить M1. Для каждой ошибки: причина → минимальное исправление → проверка.
4. Если toolchain задерживается, продолжать M2/M3: статические копии клиента и формат,
   для которого есть старый загрузчик и реальные данные 455.
5. По первому формату уточнить трудоёмкость и выбрать следующий законченный сценарий.

## Организация работы и память

Один цикл — одна проверяемая цель: определить входы/критерий готовности, провести
минимальный эксперимент, проверить, записать доказательства, обновить текущий статус.
Непроверенная гипотеза не становится фактом при переходе в новый чат.
Субагенты — только по отдельной просьбе пользователя.

| Файл/каталог | Назначение |
|---|---|
| AGENTS.md | Постоянные правила, границы действий, порядок чтения |
| docs/project-memory.md | Короткое актуальное состояние, решения, следующий шаг |
| docs/environment-audit.md | Подтверждённое окружение и границы проверки |
| docs/build-audit.md | Проекты, блокеры B01–B13, первая сборка |
| docs/next-steps.md | Ближайшая очередь, обновляемая после этапа |
| docs/roadmap.md | Долгосрочные этапы и критерии перехода |
| inventory/*.json | Воспроизводимые манифесты и сводки |
| research/ | Исследования форматов/подсистем с доказательствами |
| scripts/ | Повторяемые массовые операции и проверки |
| work/, artifacts/ | Копии, IDB, сборки; требуется отдельный backup |

Находка в бинарнике: файл/SHA-256, архитектура, image base, VA/RVA функции,
вход/выход, вызывающие функции, проверка, статус «подтверждено/гипотеза/неизвестно».
Формат данных: хеш образца, смещения/размеры, границы и обработка ошибок.
В Git — небольшие изменения и очищенные сводки, без секретов, БД, игровых бинарников
и сырых логов. Remote/push для этих этапов не нужны.

## Модель и уровень мышления

Это рекомендация для проекта, не гарантия результата на любом участке:

| Работа | Стартовая настройка | Повышение |
|---|---|---|
| Аудит, скрипты, сборка, документация | GPT-6.1 Sol в Codex, medium | high при нескольких взаимодействующих причинах |
| Реверс C++/x86, структуры, пакеты, сравнение версий | GPT-6.1 Sol, high | Astra high при противоречиях после сбора фактов |
| Сложный ABI/неизвестный алгоритм, пересмотр решения | GPT-6 Astra, high | xhigh для конкретного нерешённого вопроса |
| Сводка проверенных данных | GPT-6 Luna, high, либо существующий скрипт | Не поручать окончательные выводы о совместимости |

Codex — рабочая среда с файлами/MCP; GPT — выбранная модель. Для проекта используем
Codex внутри этой папки. Повседневно достаточно начать с Sol medium; на реверсе — high.
Настройки этим документом не изменены; доступность зависит от аккаунта/клиента.

Официальная документация на 2026-11-04 рекомендует Sol для длительной работы при
важности стоимости, Astra для наиболее сложных задач, Luna для узких повторяемых.
Повышение reasoning расходует больше времени/токенов. Конкретные уровни в нашей
таблице — инженерная рекомендация: https://learn.chatgpt.com/docs/models.

Экономия: массовые выгрузки IDA сохранять локально, в контекст давать нужные функции
и различия; не повторять инвентаризацию без изменения входов; не загружать все навыки;
закрывать по одному контракту с проверками. Max/ultra не использовать по умолчанию.
Бюджет и сроки уточнять после M1/M3 по измеренным результатам.
