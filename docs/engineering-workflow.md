# Инженерный процесс RF Online 455

14.11.2026. Новый режим: сохраняем M6 и восстанавливаем поведение 455.
15.11 пользователь разрешил root запускать локальную бету под отладчиком и
проверять исправления самостоятельно в 1920×1080. Сквозной прогон включает
одно убийство монстра, одну продажу и покупку у NPC, затем телепорт.
Приёмка пользователем остаётся отдельной. По порядку разработки:
сначала целиком одна из 12 областей, затем следующая. Первая в очереди —
«Файлы и данные», начиная с загрузчика и кэша. Идентификаторы областей сохраняются.
Root проверяет код и запускает целевые отдельные CPU-тесты без игры/графики.
RF_Online.bin не собирать до закрытия списка реализации активной области.
После этого сборка, сквозной прогон под отладчиком и исправление ошибок.
«Реализация завершена», «тесты пройдены» и «принято пользователем» различаются.
Локализации в активной разработке и приёмке — `zh-tw` и `ru-ru`.
Игровые прогоны выполняются одним владельцем клиентского сеанса.

## Контракт → реализация → сверка → пользователь

Root исследует оригинал через IDA MCP и существующие доказательства. GoMMO
используется для ресурсов, если её инструменты подходят; новый парсер не пишется
ради уже доступного просмотра. Навык reverse-engineering — основной.

Одна карточка существующего пакета содержит: наблюдаемый результат, SHA/RVA
оригинала, входы/выходы/состояния, порядок событий, сетевые/файловые форматы,
владельцев памяти, отказы и границы, подтверждённое/гипотезы/неизвестное,
разрешённые улучшения, файлы реализации и короткие действия для пользователя.
Доказательства изучаются по вызовам и данным, не только по псевдокоду.

Один агент пишет код по версии контракта. Root сверяет его с оригиналом,
интегрирует и проверяет компонент; полная сборка подчиняется ограничению выше.
Новое доказательство меняет версию контракта и список
затронутых мест; агент корректирует их. Подтверждённые части не переписываются
целиком. Два прохода — это две роли на пакет, не обещание двух проходов на всю игру.

Статусы: исследуется → контракт готов → реализовано → собрано → передано
пользователю → принято/дефект. Без ответа пользователя не считать поведение
проверенным в игре. Выдача: актуальная сборка через существующий ярлык,
короткий список изменений/известных ограничений и 3–5 проверяемых действий.
Никаких новых автоматических goals без прямого запроса.

Модернизация допускается внутри контракта: общий кэш неизменяемых ресурсов,
пакетная подготовка нужной сцены, устранение повторного разбора/декодирования,
управление временем жизни. Не загружать весь клиент навечно: RAM/VRAM и
распакованный размер различаются; нужны лимит, освобождение и инвалидация.
Общие модели/текстуры используются по ссылке, анимационные позы и состояние
персонажей не должны случайно разделяться. Экономия не считается измеренной
без данных пользователя. Порядок сетевых сообщений и игровые правила сохраняются.

Адресация: текущий 4f07a63d — Machine 014C/x86, LAA=false (заголовок проверен
14.11 без запуска). Сначала аудит указателей/знаковых преобразований и x86DLL
для LAA; отдельно аудит зависимостей/ABI для x64. На диске/в сети фиксированные
ширины и упаковка остаются прежними. x64 — развитие текущего проекта, не новый.

## Один законченный пакет

1. Выбрать наблюдаемый результат и владельца. Записать область файлов,
   исходное доказательство, подзадачи, проверку, бюджет и следующий шаг.
2. Использовать существующие код/ресурсы/доказательства. Исследовать неизвестное,
   блокирующее результат; не индексировать всё заново.
3. Изменить минимальную связанную часть с возможностью возврата. Архитектурную
   границу выделять там, где она нужна реальному сценарию.
4. Root интегрирует, собирает и сверяет код с контрактом. Пользователь
   проверяет изменённое поведение и связанный сквозной сценарий в игре.
5. Записать сборку, условия, факт/ограничение и доказательство. Закрыть пакет
   только по приёмке; обновить очередь и краткую память.

**WIP = 1 основной пакет + максимум 1 независимая задача агента.**
Агент получает непересекающиеся файлы и конкретный результат. Root владеет
сборкой и сеансом отладки. Пользователь выполняет итоговую приёмку.
Агент не меняет общие настройки, сервер или входные материалы.

Пакет рассчитан на 30–60 минут активной работы, максимум 90 до пересмотра;
это бюджет решения, не обещание завершения функции. **30 минут без нового факта
или две неудачные попытки одного подхода — остановка этого подхода.**
Зафиксировать препятствие и уже проверенное, выбрать меньший эксперимент либо
другой путь. Если нужен внешний ресурс/решение — сообщить. Не снижать критерии
молча, не объявлять цель завершённой, не накапливать одинаковые прогоны.

## Пользовательская приёмка и визуальный результат

Root использует перечисленные проверки для локальной диагностики. Пользователь
принимает результат. Визуальный ориентир сохраняется, но его
достижение не блокирует восстановление остальных функциональных контрактов.

- Игровой прогон: 1920×1080; минимум 1280×720 с записью причины и размера.
- Визуальный ориентир — Clair Obscur: Expedition 33 с узнаваемым RF Online,
  без копирования чужого искусства и переноса на UE5. Сначала эталонная картинка,
  затем глубокая оптимизация; не подменять ориентир преждевременным упрощением.
- Графика: закреплённая сцена, камера, поза, свет; сравнение до/после,
  время кадра, VRAM и RAM на той же машине. Это диагностика, сейчас без строгого
  ограничения эффектов по производительности и без обещания FPS/системных требований.
- После визуального эталона: профили CW на 500/1000/2500 участников.
  Визуальное воспроизведение толпы и реальные сетевые игроки проверяются отдельно.
- Компиляция, стенд, реальная модель и живой мир — разные уровни доказательств.
  Переключение шейдера само по себе не доказывает улучшение вида.
- Старые проверки повторять при изменении зависимостей или сигнале регрессии.
  Полную регрессию оставлять для интеграционного рубежа/M7/M9.
- Все графические переключатели работают через настройки; применение, отмена,
  сохранение и необходимый перезапуск проверяются. Неработающих обещаний в UI нет.
- Современный визуал требует материалов, текстур, света, эффектов и художественной
  оценки. Актуальная платформа — x86/D3D9. API сам по себе не улучшает изображение;
  D3D11 — кандидат до ограниченного эксперимента. Новые инструменты нужны
  при реальной нехватке текущих.

## Хранение и воспроизводимость

- Код/скрипты/малые манифесты — Git. Оригинальные данные и сервер не трогаем.
  Не публикуем и не коммитим секреты, учётные данные или полные игровые ресурсы.
- Перед очисткой: карта зависимостей, список сохраняемого и кандидатов, проверка
  уникальных исходников/артефактов. Hardlink: сумма путей не равна месту на диске.
- Храним одну текущую рабочую сборку и одну предыдущую для отката.
  Уникальные исторические доказательства сохраняем компактно с манифестом/хешами;
  если без большого файла доказательство невоспроизводимо — сохраняем и его.
- Новая копия/выходной каталог требует назначения и срока удаления. Используем
  общие неизменяемые ресурсы; не создаём полный клиент для каждой локальной проверки.
- Единый источник лимитов — [workspace-policy.json](../config/workspace-policy.json):
  весь workspace — 40 GiB логически / 75 000 файлов; work/m9 — 12 000 файлов /
  32 каталога по хешу. Автоматическую проверку ведёт root. Это пределы хранения,
  а не графики; остановиться до превышения, не удалять исходники/доказательства автоматически.
- До/после очистки записываем число путей, логический и уникальный размер,
  удалённые категории, сохранённые исключения. Удаление — после проверки
  абсолютного пути и воспроизводимости; очистка не оправдывает потерю исследования.

Очистка 13.11: workspace ≈11,54 GiB / 52 522 файла; work/m9 — 8 каталогов
по хешу / 2 079 файлов; освобождено 51,16 GiB физически. Остались 565 занятых
Windows шрифтов в work/cleanup-pending-fonts (357 452 900 байт логически).
После освобождения/перезагрузки удалить только этот проверенный остаток;
это отдельное завершение очистки, а не возобновление разработки.

Статусы очереди: active / queued / blocked / done. Done означает выполненную
приёмку со ссылкой на результат. В отчёте: что реально работает, что остаётся,
какой следующий наблюдаемый результат; не процент по количеству тестов.

## Карточка задачи и инструкция исполнителю

Иерархия: **цель → этап → задача → 2–5 конкретных действий → доказательство**.
12 областей — контроль полноты игры поперёк этапов, не 12 параллельных проектов.
Дробить задачу нужно по наблюдаемому результату, а не по каждой функции или файлу.

Для исполнителя достаточно короткой карточки:

> Задача ID: [один результат, который увидит игрок]. Основание: [текущая сборка,
> известный факт/проблема]. Менять: [файлы/подсистема]. Действия: [2–5 шагов].
> Готово, когда: [наблюдаемые условия]. Проверить: [один подходящий сценарий].
> Бюджет до пересмотра: [30–60 минут]. Сохранить: [код и компактное доказательство].
> Итог: что изменилось, что проверено, что осталось, следующий шаг.

Нужна дисциплина исполнения карточки, а не постоянное увеличение промпта.
Новый инструмент/навык добавлять только под выявленный недостаток возможностей.
Готовность графики оценивается сравнением изображения и движения; оставшийся
объём — открытыми сценариями, а не числом проверок или проиндексированных функций.
