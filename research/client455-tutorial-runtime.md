## Порядок исполнения

Если заданий нет, кадр ничего не делает. Иначе очищает указатель активного
задания; проверяет текущий ordinal, непустой список, Avatar20168 и board2286,
затем flags задания. За кадр пытается начать не более одной новой команды.
Начатая незавершённая current-команда блокирует запуск следующей. После этого
проверяется весь начатый префикс списка: команды с Begin и без Finish получают
Update. Это не означает, что обычный сценарий всегда запускает их параллельно.

Begin до вызова конкретного Start сбрасывает global cursor button, кроме
dataType16. При неуспешном Start это уже произошло, но таймер и flags не меняются.
После успешного Start вызывается timeGetTime, общий timer получает его DWORD,
input устанавливается11, owner+52 обнуляется, выставляется Begin bit1. Таймер
общий для всех команд; более поздний Start меняет начало предыдущего ожидания.
Смысл owner+52 ещё не подтверждён — в собственном типе он явно назван state52.

Bit4 завершает команду без вызова Update. Иначе завершение определяется Update.
Bit2 ставится **до** вызова Finish. Finish Message и Wait действительно пустые:
их тела побайтно совпадают, это не заглушка вместо неизвестной реализации.

Refresh сбрасывает ID задания в FFFFFFFF, его сериализованный WORD count в0,
flags команд и iterator/current. Сам список и частное состояние процессоров
сохраняются. Обход использует список; explicit GetQBI(index) после Refresh
из-за count0 возвращает null, а GetQBI(FFFF) возвращает current при его наличии.
Explicit refresh другого задания не меняет текущий ordinal сценария.

При iterator==end завершение определяется flags последней команды, без общего
ожидания всех предыдущих. Следующее задание получает Refresh в этом кадре, но
его первая команда не запускается до следующего кадра. После последнего задания
вызывается board completion, который в455 может выгрузить сценарий и изменить
Avatar stage. Собственный диспетчер допускает clear из этого callback и после
него не обращается к членам владельца.

## Сообщения и ожидания

Message Start выбирает действие0–4 по сохранённому dataType. Host получает
сообщение либо WORD reference для type4. Target default для неизвестного
dataType ничего не показывает и возвращает успех; это отдельная подтверждённая
ветка. Actual rendering/briefing/ownership остаются работой настоящего host.
Сериализованный fixed Message с dataType0–3 может содержать foreign pointer;
factory его не выдаёт за собственный HSD объект и явно отказывает.

Wait mode0 сравнивает BYTE input с полным DWORD value; совпавший input сбрасывает
в11. Mode1 сравнивает unsigned DWORD(now-start)>=value, включая переполнение.
Start и Update читают clock раздельно. Mode2 использует условия:

| value | Подтверждённая проверка |
|---|---|
| 4 | Board17 DWORD1892 и DWORD1896 оба ненулевые |
| 5/6 | Avatar BYTE614 равен0/1 |
| 7/8 | Avatar BYTE612 равен1/0 |
| 9/10 | Avatar DWORD24308 ненулевой/нулевой |

Остальные mode/value остаются в ожидании. Игровые имена этих полей и настоящие
провайдеры ещё не подтверждены: интерфейс хранит явные reference field names,
без догадок о боевом/беговом режиме.

## Проверка и ограничения

Библиотека RF455TutorialRuntime.lib SHA-256
`a758e02cb6f7a511a41dfa356596b011511f0cdc599bf655927d138ae869ba3f` собрана MSVC x86.
Собственная PE `9618bd36...`, entry RVA8100, естественный exit0. Native probe
использует recording host: проверены callback order, gates, одна новая команда
за кадр, flags/refresh/ordinal, failed Start, bit4, clock equality/wrap/reset,
message0–4, wait conditions и completion с немедленной выгрузкой.

Три реальных файла BW/CW/AR содержат1235 записей:728 создаются basic factory,
507 требуют остальных процессоров. Это coverage выбранной выборки, не процент
готовности клиента. Попытка подготовить полный реальный сценарий честно
отклоняется на первой отсутствующей команде и сохраняет прежнюю программу.
Неизвестные команды не пропускаются и не заменяются no-op.

Runtime::prepare — собственная атомарная unload+load операция. Сырые reload,
OOM, произвольная инвалидация владельца из промежуточных callbacks и остальные
поля context ещё не приняты. Source-owned структуры не повторяют binary ABI.
Полный UI, движения, создания персонажей/предметов, экипировки, боя, сцены,
Tutorial local messages и fourstage integration остаются обязательными.

В058 исправлена совместимость отчётов057/058 с kernel_sources: поле library
должно быть строкой пути, SHA — в library_sha256. Вложенный dict ломает
обнаружение канонических исходников. Формат исправлен, обе короткие пробы и
discovery20kernels проверены. Код parser057 не менялся. Новые metadata не
меняют обычную PE; её SHA по-прежнему56905e68... . Большие unchanged suites
не повторялись.
